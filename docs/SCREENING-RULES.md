# Phase 4 screening coverage and provenance

Reviewed during implementation on **8 October 2026**, rule version **2026-10-08.1**. This is deterministic partial screening for new applications. A basic match means only that all implemented checks match the supplied facts. It is not a complete eligibility assessment or government approval. Review dates are separate from publication dates and do not renew automatically when an API request runs.

PFRDA is the pension regulator’s official `.org.in` site. It is included as a reviewed static screening reference, independently of the catalog seed’s `.gov.in` URL validation. No user-supplied source URLs are accepted.

The PFRDA PDF was read directly. Its question 17 resolves APY’s upper limit as the 40th birthday, rather than the full year of age 40. Current and past tax status is explicit; household income is never substituted. The PMSBY FAQ combines an 18–70 range with termination at 70 (nearer birthday), so saved age 70 is deliberately unknown until a provider checks the exact date. PMJJBY uses new-entry age limits and does not apply renewal-to-55 rules to first-time applicants.

The UP family criteria and ministry PM-KISAN statements were readable directly. DFS insurance FAQs, PMJDY details and the UP stage table were supported by official indexed content where direct requests timed out or failed. No third-party blog was used as authority. The older PM-KISAN exclusion statement is explicitly dated and linked, with current overview evidence; full current exclusions remain an official-provider check. Source uptime and completeness are not certified. UP’s dated maintenance notice is not an eligibility rule.

UP stage selection provides the relevant official requirement for the user to confirm. It never infers a girl’s birth date, immunisation, admission or academic year from the account holder’s age/occupation. Family exceptions are not reduced to a rigid two-child rejection: the user must review and confirm the official provisions. If saved state/income describe a different family, they are not applied and the result requires clarification.

## Decision semantics

1. Unsupported catalog slug → `not_assessed` with no invented rules.
2. Any checked rule `not_met` → `criteria_not_met`, retaining all unknown inputs.
3. Otherwise any checked rule `unknown` → `needs_info`.
4. Otherwise → `basic_match`, still accompanied by limitations.

Missing fields are deduplicated by input origin/key. `false` is a real answer; missing and `null` mean unknown. Zero income is a supplied value. All results remain alphabetical. There is no score, ranking, recommendation, AI inference or automated application.

## Maintenance

Review the responsible provider’s current criteria and full guidelines before changing a rule. Resolve ambiguity conservatively as unknown. Change the rule version and review date together with sources, question wording and boundary tests. Keep browsing summaries separate from screening logic and its explicit partial scope. Do not add demographic guesses or treat a match as approval. Re-run API, browser and production audits after changes. Future catalog entries remain unscreened until reviewed rules exist.
